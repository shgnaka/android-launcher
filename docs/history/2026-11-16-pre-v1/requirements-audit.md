# 要件・仕様案の未確定点の点検

更新日: 2026-11-16。対象は [要件定義案](requirements.md)、[仕様案](spec-proposal.md)、[受け入れテスト計画案](acceptance-plan.md)。README と過去の検証記録は、旧版との差分を確認する補助資料として扱った。

結論: **全体のテストを凍結できる状態にはまだ達していない**。要件 ID とケース群の対応はあるが、同じ要件から異なる正解を作れる箇所が残っている。今回の点検は仕様書のレビューであり、アプリの不具合を再現したという意味ではない。

**後続指示の反映:** GAP-02はホーム1画面と収容不可エラー、GAP-03はホームへの復帰と検索語の破棄、GAP-04はホームのアプリ名にメニューを出さない、GAP-05は非表示管理以外で表示しない、GAP-07は対象なし非表示・複数対象を横スワイプ・操作は記号、GAP-08は既存定義を維持して今日／直近24時間を選択する、という方向で解決した。GAP-17に一覧キャッシュ、GAP-29に文字サイズ変更を追加した。ウィジェットの最低合格ラインは実験後にユーザー確認が必要。以下は点検当時の記録。

## 1. 確定済みと、案のままのもの

ユーザーの明示的な回答で確定している hide app の選択は、ホーム・一覧・検索のすべてから隠すこと、一覧の長押しを操作メニューへ変えること、ホーム登録と順番を保持して解除時に戻すこと。基準実機は OPPO Reno7 A / Android 13。

アプリ単位の非表示、再インストール後の維持、登録済みウィジェットを残すこと、並べ替えの具体例、都市名検索と30分更新、画面時間の集計方式、破損時の復旧、性能の数値目標は、具体案がある段階。会話の続行だけを採用の意思表示として扱わない。

以下は追加する新機能の一覧ではない。「今回の対象外」と決めれば閉じられる項目、既に案があって採否だけ残る項目、製品の振る舞いを補う必要がある項目、テスト側の判定方法を決める項目を区別する。

## 4. 特に注意する整合箇所

### ホームの情報量とジェスチャー

多数のお気に入りや長いウィジェット情報を許し、縦方向の動きを常に一覧を開く操作として扱うと、ホーム下部の情報へ到達する方法がなくなる。反対に、ホーム末尾までスクロールしなければ一覧へ進めない方式は NAV-01 の意図に合わない。表示量・操作領域・優先順位を一組で決める必要がある。

### メディアの要求と外部アプリの結果

「次へを要求した」と「次の曲がある再生対象が曲を変更した」は異なる期待結果。対応していない外部アプリも含めて必ず曲を変えるというテストにはしない。一方、単にボタンが押せたことだけで連携成功ともしない。制御された再生対象で何を観測するかを決める。

### 画面時間の不足状態

数値を出せない場合の表示案はあるが、正常な履歴があるときに必ず数値を出す条件が必要。午前0時の状態を判断できる履歴、途中からしかない履歴、端末が停止していた時間を区別する入力例を先に作る。

### 性能の例外と応答の意味

1万件では検索300msまで許す案を、入力100ms制限からどう扱うかを定める。検索欄が入力に応答する時刻、結果が確定する時刻、通信が完了する時刻を混ぜると、実装前に作ったはずのテストでも判定を後から動かせてしまう。

### 旧版の説明と次版の変更

READMEの長押しによる直接登録、ウィジェットのキャンセル後の手動削除、緯度経度による地域設定などは、旧版についての説明。新しい案との差を直ちに仕様矛盾とは数えない。新しい仕様を採用した段階で、対象版と変更点を明確にして更新する。

## 5. 決める順序の提案

1. GAP-01で今回の範囲と採用済みの仕様を確定する。
2. 使い方を変える GAP-02〜08を決める。特にホームのジェスチャー、画面復帰、非表示の例外、ウィジェットとメディアの最低限の動作。
3. 保存と復旧の GAP-09/10を決める。
4. GAP-14〜30の境界条件を、その機能の具体例・状態表へ反映する。
5. GAP-11/12/13/31の計測・観測・実行環境を固定し、受け入れケースを更新した後に実行可能なテストを作成・凍結する。

使い方に関わる選択は相談し、計測や自動判定の技術案は実装担当側で具体化して提示する。この点検で新しい仕様を承認済みに変更したり、既存のテスト・製品コード・APKを変更したりはしない。
